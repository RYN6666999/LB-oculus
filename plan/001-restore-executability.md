## 核心判斷

**不修任何一個 bug。這一案只做一件事：讓「壞掉」變得可見。**

理由是實證的 —— 複驗發現的 16 條裡，**只有 1 條會發出聲音**（`dbp ls` 的 KeyError）。
其餘 15 條全是靜默的：install.sh 印綠勾、指標永遠 0%、帳本消失無抗議、
sweep 看不見自己、risk 對自己瞎。

> **如果先修那個吵的（`ls` KeyError），剩下 15 條靜默失效就再也沒有人會發現。**
> 你會得到一個「跑起來很順、指標永遠 0%、帳本可能根本沒在記」的系統 ——
> 比現在更危險，因為現在至少 `ls` 會爆給你看。

所以順序是：**先讓壞掉會叫，再去修壞掉。**

## 要解決什麼（僅此三項）

### 1 · shebang → `#!/usr/bin/env python3`

`bin/dbp`、`hooks/dbp-risk-gate`、`hooks/dbp-autocapture` 共三行。

這是所有後續工作的前提。不修，在任何非 macOS 環境上，
剩下 15 個洞連復現都做不到。

### 2 · `install.sh` 的綠勾改由「執行」定義

現在：`ln -sfn` 後印 ✓，判定用 `test -e`。
改成：link 完**真的執行一次**，跑不起來就印警告並讓 `install.sh` 非零退出。

```sh
verify() {           # 產出者不得自驗 —— link 是一條路，執行是另一條
  if "$1" --help >/dev/null 2>&1; then echo "  ✓ $1"
  else echo "  ✗ $1 裝上了但跑不起來（exit $?）"; FAILED=1; fi
}
```

**這一項是整案的核心。** 它不修任何 bug，但它讓 install.sh 停止對自己說謊。

> `install.sh` 現在正在犯 `README:38` 自己寫的那條錯：
> `ln -sfn` 產出 symlink，`test -e` 驗 symlink —— 同一條路驗，等於沒驗。

### 3 · 第一個 smoke test

16 條裡至少 11 條可被一個 30 行測試抓到。
**零測試是這 16 條的共同成因，不是第 17 條。**

必須包含的斷言（每一條都對應一個已驗證的洞）：

| 測項 | 對應 |
|---|---|
| `install.sh` 後 `dbp --help` exit 0 | P0-0 |
| `dbp ls` 在 ledger 存在時 exit 0 | P0-1 |
| `dbp fix` 後 `stats` 的 % > 0 | P0-3 |
| `dbp stats` 總數 == 真 bug 數 | P0-1b |
| `dbp risk bin/dbp` 有輸出 | 新洞 E |
| `dbp sweep .` 掃到的檔數 == repo 檔數 | P2-b |
| `dbp done <不存在的id>` 非零退出 | P2-c |
| `dbp <未知子指令>` 非零退出且不寫帳本 | 新洞 D |
| `_runs.jsonl` 不含 `sk-` 樣式字串 | P1-6 |
| Bash 改檔 payload 會進 `_edits.jsonl` | P0-2 |
| `dbp` 不存在時 gate 仍寫 `_edits.jsonl` | 新洞 A |

## 驗收方式（產出者不得自驗）

**我改的是 shebang 與 install.sh，所以不准用「讀 install.sh」驗。**
必須從乾淨環境、走安裝後的路徑：

```bash
# 1 · 乾淨環境重裝（不能踩在既有殘留上）
rm -rf ~/Developer/LB-oculus ~/.local/bin/dbp ~/.claude/hooks/dbp-* ~/.debugpedia
git clone <repo> ~/Developer/LB-oculus && cd ~/Developer/LB-oculus && ./install.sh
echo "install exit=$?"        # 必須 0

# 2 · 換一條路驗（不看 install.sh 印什麼，直接執行）
dbp --help  >/dev/null; echo "dbp exit=$?"                    # 必須 0
echo '{}' | ~/.claude/hooks/dbp-risk-gate; echo "gate=$?"      # 必須 0

# 3 · 反向驗證 —— 這條最重要
sed -i '1s|.*|#!/nonexistent/python3|' bin/dbp && ./install.sh
echo "故意弄壞後 install exit=$?"    # 必須非 0，且印出 ✗
# 一個永遠 pass 的檢查等於沒有檢查

# 4 · 測試必須被證明會失敗
#    注意：tests/smoke.sh 是本案要「建立」的檔，執行前它不存在。
#    2026-07-27 sweep 把這裡報成死引用 —— 那是真陽性，我在寫案子時
#    就犯了本次複驗抓到的幻影引用同型錯誤。已記進 ledger。
bash tests/smoke.sh; echo "baseline=$?"                 # 建立後應為 0
git stash && bash tests/smoke.sh; echo "注入舊bug=$?"    # 必須非 0
git stash pop
```

**第 3、4 步是驗收的核心。** 沒跑這兩步，這一案不算完成 ——
一個沒有被證明會失敗的檢查，不能證明任何東西。

### 與預期的落差

**預期 bug #1（`--help` 選錯）—— 命中，且比預期嚴重得多。**
不是「假綠」，是 `dbp-risk-gate --help` 在無 stdin 環境**永久掛住**（實測 >120 秒）。
照本案原本寫的 `verify()` 去做，`install.sh` 會直接凍結 ——
**一個為了偵測失敗而加的檢查，自己變成更糟的失敗。**
處置：`</dev/null` 而非 `timeout`（macOS 預設沒有 `timeout`，這是預期 bug #3 的同一族）。

**預期 bug #2（`set -e` 改 `FAILED` 會漏錯）—— 命中。**
`rc=$?` 隔著 `if` 複合指令取，拿到 if 的 0 而非真實 127。
`install.sh` **確實**非零退出了、**確實**印了 ✗ —— 所以粗看是成功的。
但它報 `exit 0`，會把人指向查權限、查路徑，永遠想不到是 shebang。
**「有報錯」不等於「報對了」。** 已修，並在 attack 001 加了診斷正確性斷言護著。

**預期 bug #7（漏驗目錄型掛載點）—— 提前命中，寫的時候就補了。**

**預期 bug #4（污染真帳本）—— 沒發生，但防線的做法改了。**
原本打算「小心設好 `DEBUGPEDIA_DIR`」。那是宣稱。
改成 A13：跑前存真帳本指紋、跑完比對，不一致就 **exit 2**（不是 1 —— 不可逆傷害用最嚴重那級）。

**預期 bug #5（斷言寫死數字）—— 沒發生，因為預先讀了這一欄才避開的。**
所有數字都從 fixture 或「我剛剛種了幾筆」推導。**這一欄本身起了作用。**

**未驗證：預期 bug #3（macOS/Linux 差異）、#6（CI 中斷）。**
#3 只在 Linux 跑過 —— 而它的成因跟本案最大的洞完全相同。已記 `dbp open`。

**計畫外的落差：斷言表照抄產生了一條假斷言。**
表上那條「`dbp risk bin/dbp` 有輸出」我照抄實作，結果它通過了，被 harness 報成 DRIFT。
換一條路查才發現：`risk bin/dbp` 沒有副檔名，走的是 `base` 比對（`"dbp" in "bin/dbp:436"`），
**本來就會中，跟 `len(stem) > 3` 那個洞無關**。那條斷言驗不到它宣稱要驗的洞，而且永遠會綠。

> 我在寫一支專門抓假綠的測試時，自己先產了一個假綠 —— **而且是照抄本案來的。**
> 鐵律一：抄寫是排程好的未來謊言。**連自己的計畫案也不能抄。**

處置：改打 `risk bin/dbp.py`（同 stem、不同 base），並加 A06b 當假紅防線 ——
否則把 `>3` 改成 `>=3` 的人可能讓 A06 因為「對所有檔都喊有前科」而變綠。

### 推翻了本案哪些判斷

**1 · 推翻驗收第 4 步的 `git stash` 手法。**
`tests/smoke.sh` 是本案新建的檔，`git stash` 會把測試自己一起收走 ——
**驗收指令會刪掉它要驗的東西。** 改為精準還原個別舊 bug。

**2 · 推翻「baseline 應為 0」。這是本案的自我矛盾。**

| 本案寫的 | 位置 |
|---|---|
| **不修任何一個 bug** | 核心判斷 |
| `bash tests/smoke.sh` → **建立後應為 0** | 驗收第 4 步 |

兩者不可能同時成立。一個不修 bug 的 repo，寫一套抓得到那些 bug 的測試，
baseline 不可能是 0。硬要 0 只有兩條路，兩條都是這個 repo 自己禁的：
偷偷修（違反核心判斷，且 15 條靜默失效會失去護欄）、
或偷偷跳過（「抑制必須可見」的反面，牆上開洞還不掛牌）。

處置：走第三條路，語意跟 `redteam/` 同一套 ——
每條斷言自帶 `EXPECT`（`PASS` / `KNOWN_FAIL`），**已知洞紅了算通過，綠了算 DRIFT**。
現況 16 條：通過 6 · 已知紅 10 · exit 0。

> **這個矛盾正是「存每一案」的價值。**
> 如果本案沒被寫下來，我今天會為了讓 baseline=0 而偷偷修兩個 bug，
> 而那正是本案花最多字反對的事 —— 我會照著自己的計畫案，做出計畫案禁止的事。

**3 · 沒有推翻的：核心判斷本身是對的，而且比預期更對。**
16 條裡 10 條是已知紅。若當初先修那個吵的（`ls` KeyError），
這 10 條會全部留在靜默狀態，而且再也沒有理由去寫這支測試。
