# LB-oculus · 陰陽眼

跨專案的防幻覺工具鏈。目標是讓 AI 的開發行為導向「更少 bug」，而不是導向「看起來完成」。

`LB-nexus · 律令` 管單一專案的關卡。這套管所有專案共用的鐵律，語言無關、專案無關。

---

## 讀這份文件的規則

**本文件不寫任何當前數值。** 帳本筆數、覆蓋率、自違規數、錨點內容、還沒做完的事——一律只寫產生它的指令。

理由是實測出來的：這份 README 的前一版寫「抓出 41 個錯誤」，而同一天 `plan/balance-log.md` 寫 37，更早的版本寫 31。三個數字在三份文件裡各自凍結，沒有一個是錯的，也沒有一個是現值。

兩種數字要分開對待：

**歷史事件的數字可以寫。** 「那個常數比真值大 15 倍」，事件結束了，不會變。

**當前狀態的數字不准寫。** 一律換成 `→ 現值：<指令>`。

## 鐵律零 · 交付的定義是對面收到

我讀不到的東西等於沒發生。不是「做了但沒被看到」，是沒發生。

主詞在這裡換掉了。其他三條都是「你要做到 X」，由行動方宣布；這一條是「對面要能查到 X」，行動方宣布不了。

> **案例一。** 一輪回報五個 ✅，五件事真的都做完了，本機 `ANCHORS.md` 也真的更新了。但沒 push。
> 從審核方的角度，那一輪的產出是零。錨點的意義是「存在寫帳的人動不到的地方」，它當時存在寫帳的人動得到的地方。

> **案例二。** 上一輪提示詞第一項是「補 CI」。回報的四件事裡完全沒提，也沒說沒做。
> 它是靜靜從清單上消失的，不是被拒絕的。所以現在規定：清單每一項都要有結論，做完或沒做，沒做要寫原因。跳過視同違規。

零號在前三條之前。前三條都預設證據已經在桌上了。

→ 本輪有沒有落地：`gh run list` 與 `git log origin/<branch> -1`

## 鐵律一 · 事實只能推導，不能複製

抄一次就等於預約了一個未來的謊。抄本不跟著本體變，也沒人回頭對。

> **案例一。** 某支腳本的註解抄了另一支的常數，抄的值比真值大 15 倍，而且兩邊變數名一模一樣。
> 這證明「統一術語」解決不了問題——病不在講法不同，在那個數字是打進去的，不是讀出來的。

> **案例二。** prev 的算式一度同時存在三個地方（`bin/dbp`、`hooks/dbp-risk-gate`、`hooks/dbp-autocapture`）。
> 三份 `sha256(prev_line)` 邏輯，改其中一份就漂移，而漂移在鏈斷掉之前完全看不出來。

> **案例三（這份文件自己）。** 前一版 README 把 `audit/ANCHORS.md` 的內容原封抄進來，
> 而 ANCHORS.md 第一行就寫「自動產生，不要手改」。抄的那一刻它就開始落後。

**判斷方法**：這個值是讀出來的，還是打出來的。打出來的一律違規。

**檢查**：`redteam/attacks/012` grep 全 repo 找 sha256 + 讀最後一行的組合，出現在凍結核心以外就是 BREACH。

## 鐵律二 · 0 信心路由

預設任何開發行為第一次就有問題，換一條路驗過才算。**產出者不得自驗。**

> **案例一。** `install.sh` 印六個 ✓ 且 exit 0，而 `dbp` 和兩個 hook 全部 exit 127。
> 綠勾由 `test -e` 定義，不是由執行定義。`ln -sfn` 產出 symlink，`test -e` 驗 symlink——同一條路。

> **案例二。** 「驗過了」才推 commit，驗法是跑驗證腳本，但那支腳本只驗 edges，node 欄位一個字都不看。
> 同角度驗等於沒驗，一次放行三個假宣稱。

> **案例三。** GitHub 分支顯示 `protected: true`。展開看 `enforcement_level: "off"`、`contexts: []`——
> 保護開著，但不強制任何檢查。旗標為真，實際內容為零。

「路由」是重點：驗證要被導到**另一條路**，不是同一條再走一遍。

延伸的預設：**AI 的任何開發行為 100% 一定有 bug**，差別只在大或小、短期或長期。

直接後果：修正規劃案本身也是 100% 有 bug 的宣稱，所以也要存檔對帳。見 `plan/`，每案先寫「預期會出什麼 bug」，事後回填實際。那個落差是判斷力唯一的得分表。

## 鐵律三 · debug 百科

兩類東西同級收錄：

**(A) 任何被抓到的錯誤**——AI 抓、人抓、機器抓都算，一次就記。
**(B) 應做而還沒做的事**——同級，不是附屬。

| | 會不會叫 | 結果 |
|---|---|---|
| bug | 會（紅字 / exit code） | 被處理 |
| 未收尾 | 不會 | 不被處理，然後長大 |

bug 是急症，未收尾是慢性病。

> **案例。** 這份 README 改版時，作者用三條鐵律掃出自己 10 條違規，打算直接改掉不記。
> 改掉不記等於下次還會犯，而且沒人知道犯過。抓到就記，不管是誰抓的、有沒有當場修。

標記成本要低到不會有人偷懶跳過。忙的時候會跳過，而忙的時候正是最會出錯的時候。

→ 現在有多少筆、多少未收尾：`dbp stats` / `dbp open`

## 鐵律之間怎麼互抓

單獨一條都能繞過。有用的是它們互咬的那幾個小迴圈。

**法二抓法一。** 換一條路驗，才發現註解裡那個常數是抄的。只讀註解永遠對得上，因為它自己跟自己一致。

**法一抓法三。** `audit/LEDGER-SNAPSHOT.md` 必須由 `export.py` 產生。手抄一份到 markdown 就是法一禁的事，而且抄完就開始腐朽。

**法三抓法二。** `dbp rules` 跑出「同路驗證」×N，就知道這不是零星 bug 而是一個類別，該從結構上關掉。關掉的方式是長出一支紅隊攻擊，不是再修一個個案。

**法零抓全部。** 前三條做得再好，沒推上去等於零。

**紅隊抓法二自己。** 兩支 canary 監視 harness 會不會說謊。攻擊腳本自己壞掉（BROKEN）比洞還在（BREACH）嚴重，因為那代表你什麼都不知道。

完整迴路：

```
錯誤 → 記一筆 → dbp rules 歸類 → 到閾值 → 變成機械檢查 → 該類永遠不再發生
```

學習以「文件」收尾等於沒落地，以「閘」收尾才算落地。

## 落地的操作定義

學到的東西必須在**動手的那一刻**出現，不是在**想起要查的那一刻**。那兩個時刻從不重合。

| | 落地了嗎 |
|---|---|
| 寫成文件 | ❌ 要人想起來讀 |
| 記進 log | ❌ 要人想起來查 |
| 手動 `dbp risk` | ❌ 同上 |
| 改檔當下自動跳出來 | ✅ 不需要想起來 |

實測靠自律的記錄執行率遠低於一半，而且全部發生在「停下來時」或「被罵時」。所以查詢也不能靠自律。

→ 精確數字：`dbp stats`（不寫在這裡，會漂移）

## 基礎設施

五樣。鐵律靠它們才有牙齒，沒有它們就只是文字。

### 1 · 雜湊鏈（凍結核心 K）

四個函式 `chain_prev` / `read_chain` / `verify_chain` / `chain_append`，全部只在 `bin/dbp`。

**只能改 bug，不能改演算法**，直到換簽名演算法那種跨世代升級，而升級本身也要寫成計畫案。

為什麼凍結：格式一改就要重寫歷史。「改進格式」是最好用的攻擊入口，因為它長得像進步。核心只准縮不准長，外圈（紅隊、cron、plan）愛怎麼增生都行。

→ 有沒有漂移：`./redteam/attacks/012-*.sh`

### 2 · 帳本

`~/.debugpedia/ledger/_edits.jsonl` 和 `_runs.jsonl`，append-only，`sappnd` 鎖。

`_runs` 由 zsh `preexec` 寫，`_edits` 由 Claude Code 的 PreToolUse hook 或 git `pre-commit` 寫。pre-commit 是降級方案，它是事後補登，抓不到沒 commit 的編輯。

> **已知限制。** 兩本帳都在 agent 家目錄，有 Bash 就有筆。
> 實測三種攻擊全成功：偽造假 pytest 證據、`grep -v` 滅證、整本移走而 `dbp stats` 零抗議。
> 真正獨立的那本是 git history 和 CI 的 exit code，不是這兩本。

→ 現況：`dbp verify-chain --all`

### 3 · 錨點

帳本某一刻的指紋，存在寫帳的人動不到的地方。

格式 `<type> <hash> <count> <timestamp>`。

**`count` 不是裝飾。** 沒有它就擋不住截尾攻擊——砍掉帳本最後 N 行，前面的雜湊完全一致，只驗「這個 hash 存在嗎」會通過。`verify-chain --anchor hash:n` 要求該 hash 出現在第 n 筆位置，且總筆數不少於 n。這是紅隊 `011`。

**去重只比 `<type> <hash> <count>`，時間戳不算。** 一天跑兩次而帳本沒動，第二次要印「無變化，跳過」並 exit 0，不 commit。否則真的變動會被每日雜訊淹掉。

**存哪裡**：`audit/ANCHORS.md` 推到 git，另外鏡一份到手機。存在本機硬碟的錨點不是錨點。

→ 現值：讀 `audit/ANCHORS.md`。本文件不複製它（見「讀這份文件的規則」）。

### 4 · 紅隊

`redteam/attacks/`，加兩支 canary。`./redteam/run.sh` 隨時重跑。

語意是反的：**BREACH（攻擊成功、洞還在）才符合預期。** 洞消失（SEALED）要停下來查是真修好還是攻擊瞎了。BROKEN 最嚴重。

結果碼、canary 機制、攻擊清單見 `redteam/README.md`，本文件不複述。

→ 現有幾支、各自結果：`./redteam/run.sh` 或 `redteam/INDEX.md`

### 5 · CI

`.github/workflows/ci.yml`。每次 push 在 ubuntu 和 macos 兩個 runner 上跑 `install.sh` / `tests/smoke.sh` / `redteam/run.sh`，結果顯示在 PR 上，跑的人改不到。

這是鐵律零唯一的執行機制，也是唯一「測試的人不是被測的人」的地方。沒有它，前四樣的驗證都還是行動方自己宣布的。

配套是分支保護，而且要注意分支保護本身會假綠——`protected: true` 可以在 `enforcement_level: off` 的情況下成立。要驗的是 `required_status_checks.contexts` 裡真的有東西。

→ 存在與否：`gh api repos/:owner/:repo/contents/.github/workflows`
→ 保護是否真的強制：`gh api repos/:owner/:repo/branches/main/protection`

## 十一個假綠的形狀

都在這台機器上真的發生過，不是假想。

1. **存在不等於能跑。** `test -e` / `which` 過了，實際執行 exit 127。只有真的執行過才算數。
2. **有輸出不等於有動作。** 指令回了東西，但什麼都沒做。驗效果，不驗回應。
3. **沒跑成不等於通過。** 前置條件缺了要回「未知」（較高的 exit code），不是回 OK。
4. **靜態數字是死指標。** `fix()` 更新 record 卻沒更新 fix 欄位，百分比掛在 0 掛了幾個月。發布前先問：這個數字會不會變。
5. **崩潰卻 exit 0。** 例外被吞掉，CI 照樣綠。
6. **重複的事實會漂移。** 表格和 README 對不上。留單一來源，其他地方連過去。
7. **宣稱有但實際沒有。** 註解寫「配合 pre-commit 使用」，repo 裡沒有 pre-commit。宣稱前先 grep。
8. **檢查器把自己排除在外。** `SWEEP_EXT` 只認副檔名、`risk()` 要求 `len(stem) > 3` 而 `len("dbp") == 3`——三個核心檔對 sweep 和 risk 完全不存在。**它不是豁免自己，是看不到自己，這比豁免更難發現：豁免會留下一條規則，看不到不留痕跡。**
9. **閘只擋主路。** risk-gate 擋 Edit/Write/MultiEdit，`sed -i` 和 heredoc 直接繞過。等價路徑要列完。
10. **假紅會膨脹。** 一個會誤報的閘會訓練人忽略所有閘，當 P0 修。
11. **旗標為真不等於規則有效。** 分支 `protected: true`，但 `enforcement_level: "off"`、`contexts: []`。要驗的是規則的內容，不是開關的狀態。

→ 完整條目與各自的重跑指令：`audit/LEDGER-SNAPSHOT.md`（機器產生）與 `audit/2026-07-27-verification.md`

## 三層測試的分工

| 層 | 問什麼 | 什麼叫失敗 |
|---|---|---|
| `tests/smoke.sh` | 裝完之後功能還在嗎 | 修好的東西又壞了（NEW_RED） |
| `redteam/` | 已知的洞今天還在嗎 | 狀態變了而沒人知道（DRIFT） |
| `cron/` | 錯誤史裡有沒有還沒被攻擊涵蓋的結構 | 排程安靜地什麼都沒做 |

第三層是**進料**不是判決：只產候選，不自動寫進 `redteam/attacks/`。理由是一個有完整 repo 上下文的 agent，在專門偵測假綠的程式碼裡產了五個假綠。假紅在紅隊裡的傷害是複利的。

### 為什麼 smoke.sh 不是全綠才算過

`plan/001` 決定先讓壞掉會叫，再去修壞掉。所以測試建立的那一刻，已知的洞必須是紅的。每條斷言自帶 `EXPECT`：`KNOWN_FAIL` 紅了算通過，**綠了算 DRIFT**（洞被修掉卻沒人更新宣告）。

硬要 baseline 全綠只有兩條路，兩條都是這個 repo 自己禁的：偷偷修掉，或偷偷跳過。

> 一支永遠全綠的 smoke test 是最貴的謊言。

**反過來也一樣：一條永遠紅的門檻等於沒有門檻。** 鏈覆蓋率如果把接地前的舊資料算進分母，那個比例永遠不會達標，遲早有人把閾值調鬆或加 `|| true`。分母只算接地後，接地前的筆數當資訊印出來。

→ 現在的通過/已知紅比例：`./tests/smoke.sh`

## 出場條件

兩個都成立才搬去 neuralis 實戰。

**A. 自違規數 < 10。** 這些是「工具違反自己的規則」，也就是它的病例庫和它的行為之間的差距。差距大的時候搬出去，等於把病帶到新環境。

> **已知標籤漂移。** 規定的標籤是 `self-violation`，實際錄入用的是 `self`，`export.py` 搜前者永遠回 0。
> 帳看起來很乾淨，其實是標籤對不上。這本身就是第 4 條假綠。

**B. 這一輪新抓到的 ≤ 新產生的。** 邊際效益翻負的那一輪就停。

**防作弊條款，跟門檻本身一樣重要：**

標籤只准往上貼，不准往下撕，要更正就開新條目。每輪同時報自違規數和總錯誤數，只報其中一個不算。自違規 +0 但總錯誤 +3 以上，要在 `plan/balance-log.md` 寫清楚為什麼那些不算自違規——沒貼標籤就是漏報。

兩個條件都達標後，換一個沒用過的模型，只給 repo 連結和「找假綠」四個字，跑一輪。它抓到 5 條以上就算沒達標，先修完再說。

→ 現值：`plan/balance-log.md`（每輪更新）

## 安裝

```bash
git clone <repo> ~/Developer/LB-oculus
cd ~/Developer/LB-oculus && ./install.sh
./install-shell-hook.sh        # zsh 指令帳，idempotent
```

symlink 安裝，不複製。複製會產生第二份，兩份會漂移。

Claude Code hooks 要自己加進 `~/.claude/settings.json`（`install.sh` 只放檔案，不動你的設定）。設定範本見 `hooks/settings.example.json`，本文件不複製一份——複製的那份會跟範本漂移，這正是法一。

兩個 hook 都永遠 exit 0、永遠不擋。會擋住工作的 hook 最後一定會被關掉。

> settings.json 在 session 啟動時載入，中途改不生效。

## 用法

```bash
dbp "一句話講清楚是什麼錯"          # 記一筆
dbp "…" -w file.py:42 -t yaml,quoting -k machine
dbp fix <id> "後來怎麼解的"

dbp open                            # 未收尾清單，開場收尾各跑一次
dbp open "還沒驗證的事" -b "等服務重啟"
dbp done <id> "怎麼收的"

dbp risk <檔案>                     # 動手前：這個檔以前在哪摔過
dbp rules                           # 歸納：哪些類別重複出現
dbp sweep [目錄]                    # 死引用 / 死 commit / 腐朽宣稱
dbp verify-chain --all              # 兩本帳的鏈完整性
dbp anchor --all                    # 產生錨點
```

## 設計約束

都是踩過才寫下來的。

永遠 exit 0，會中斷工作的記錄工具最後會被關掉。沒事就完全安靜，每次都講話的東西會被當雜訊。假紅當 P0 修。抑制必須可見——每個豁免規則都是牆上的洞，洞可以有，但不能沒人知道它在。規則必須能套在自己身上。

法零指標：**豁免的成長速度 vs 真正修復的成長速度。** 比值上升代表在調鬆閘門，不是在修對問題。

## 已知還沒做到的

這一節不手寫。清單在 `dbp open`，README 只說明為什麼有些項目長期掛著：
