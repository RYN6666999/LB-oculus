# 修正規劃案 · plan/

> **前提（鐵律二的極端化）：預設 AI 的任何開發行為 100% 一定有 bug。**
> 不是「可能有」，是「一定有」。差別只在**大或小**、**短期或長期**。
>
> 所以修正案的功能不是「說明我要修什麼」，是**「留下一個能被事後對帳的承諾」**。
> 沒有存檔的規劃案，等於沒有規劃 —— 因為沒人能回頭問「你當初說會怎樣」。

---

## 為什麼要存每一案

修正案本身就是一個**宣稱**（「我認為這樣改會解決問題」）。
既然預設 100% 有 bug，那這個宣稱也 100% 有 bug。

存檔讓下面這件事變得可能：

```
案 001 說「改 A 就能解決 X」
   ↓ 執行
案 002 發現「X 沒解決，因為 A 帶出了 Y」
   ↓
→ 這條路徑被記錄下來 = 判斷力的訓練資料
```

**不存檔，每次都是第一次判斷；存檔，判斷會累積。**
這跟鐵律三對 bug 做的事完全同構 —— 只是對象從「錯誤」換成「我的判斷」。

---

## 命名

```
plan/NNN-短標題.md          NNN 三位數流水號，永不重用、永不刪除
```

**改變主意不刪舊案，開新案並在新案寫明推翻了哪一案。**
刪掉的案子沒有留下「我曾經這樣想」，那正是鐵律一禁的事 ——
歷史被改寫，就沒有東西能證明判斷有在進步。

## 每案必備欄位

| 欄位 | 為什麼必填 |
|---|---|
| **狀態** | 草案 / 待批准 / 執行中 / 已完成 / **已被推翻** |
| **要解決什麼** | 指向 ledger 的具體 id，不寫模糊的「改善品質」 |
| **不解決什麼** | 沒有這欄，範圍會蔓延，最後沒有一項做完 |
| **驗收方式** | **必須是別人能重跑的指令。** 沒有這欄的案子不准執行 |
| **預期會出什麼 bug** | 100% 前提的直接後果。事後對照這欄，判斷力才有得分 |
| **事後回填** | 執行完寫實際結果。**與「預期」的落差就是最有價值的資料** |

## 鐵律二在這裡怎麼落地

> **產出者不得自驗。**

寫規劃案的人 **不能** 用「我照案子做完了」來驗收自己。
驗收方式那一欄必須是**換一條路**的指令：

| 產出方式 | 不可以用來驗 | 應該用來驗 |
|---|---|---|
| 我改了 `install.sh` | 再讀一次 `install.sh` | 真的跑 `./install.sh` 然後 `dbp stats` |
| 我加了 `test -x` | `grep test -x install.sh` | 故意弄壞 shebang，看它有沒有報 |
| 我寫了測試 | 測試通過 | **故意注入已知 bug，看測試會不會紅** |

最後一列是最重要的：**一個沒有被證明會失敗的測試，不能證明任何東西。**
