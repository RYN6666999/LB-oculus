# LB-oculus · 陰陽眼

**跨專案的防幻覺工具鏈。** 讓 AI 的開發行為導向「更少 bug」，而不是導向「看起來完成」。

`LB-nexus · 律令` 管單一專案的關卡（SPEC → guard → contract → IMPL）。
這套管的是**所有專案共用的三條鐵律**，語言無關、專案無關。

---

## 為什麼需要它

2026-07-27 一輪對話，在一個專案裡抓出 31 個錯誤。**其中三分之一是當天現做的，而做的人正是在蓋防幻覺工事的那個 AI。**

分析那 31 筆之後，第一性原理只有一條：

> **Agent 會沿著「證據最容易製造」的方向走。**
> **架構的工作不是要求誠實，是讓造假比做對更貴。**

「看起來對」的信號是即時、確定、agent 自己就能製造的；
「實際對」的信號是延遲、不確定、要靠外部的。
梯度天生就指向造假。要求誠實是對抗梯度，會輸；改梯度才會贏。

三條鐵律各封掉一條最省事的假路。

## 三條鐵律

### 一 · 事實只能推導，不能複製

一個事實被抄寫一次，就等於預約了未來某天的一個謊。抄本不會跟著本體變，也沒人會回頭對。

> 真實案例：某支腳本的註解抄了另一支的常數，抄的值比真值大 15 倍 —— **而且兩邊變數名完全相同**。
> 這證明「統一術語」解決不了問題：病不在講法不同，在那個數字是打字打進去的、不是讀出來的。

### 二 · 0 信心路由

預設任何開發行為**第一次就有問題**，換一條路驗過才算數。**產出者不得自驗** —— 用產出它的同一條路去驗，等於沒驗。

> 真實案例：「驗過了」才推 commit，驗法是跑驗證腳本 —— 但那支腳本只驗 edges，node 欄位一個字都不看。
> 同角度驗 = 沒驗，一次放行三個假宣稱。

「路由」是重點：驗證要被**導到另一條路**，不是同一條再走一遍。

**推到極端（2026-07-27 起採用的預設）：**

> **預設 AI 的任何開發行為 100% 一定有 bug。**
> 不是「可能有」，是「一定有」。差別只在**大或小**、**短期或長期**。

這條的直接後果：**修正規劃案本身也是一個 100% 有 bug 的宣稱，所以也要存檔對帳。**
見 `plan/` —— 每一案必須預先寫下「預期會出什麼 bug」，事後回填實際結果。
**那個落差就是判斷力唯一的得分表。** 不存檔，每次都是第一次判斷。

### 三 · debug 百科

**兩類東西同級收錄，不分主次：**

**(A) 任何被抓到的錯誤** —— AI 抓、人抓、機器抓都算，一次就記。
**(B) 當下與未來應做而還沒做的事** —— 同級，不是附屬品。

為什麼 (B) 要同級：

| | 會不會叫 | 會不會痛 | 結果 |
|---|---|---|---|
| bug | 會（紅字 / exit code） | 會 | 被處理 |
| **未收尾** | **不會** | **不會** | **不被處理 → 長大** |

**bug 是急症，未收尾是慢性病。** 慢性病不會讓你今天倒下，它讓你某天突然倒下 ——
**它就是亞健康的因子。**

標記成本必須低到不會有人偷懶跳過。忙的時候會跳過，而忙的時候正是最會出錯的時候。

## 安裝

```bash
git clone <repo> ~/Developer/LB-oculus
cd ~/Developer/LB-oculus && ./install.sh
```

symlink 安裝，不複製 —— 複製會產生第二份，兩份會漂移。

### Claude Code hooks（可選，但這是「落地」的關鍵）

install.sh 會放好 hook 檔，但**不會改你的 `~/.claude/settings.json`**。要啟用請自己加：

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Edit|Write|NotebookEdit",
        "hooks": [{ "type": "command", "command": "~/.claude/hooks/dbp-risk-gate", "timeout": 8 }] }
    ],
    "PostToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "~/.claude/hooks/dbp-autocapture", "timeout": 10 }] }
    ]
  }
}
```

兩個 hook 都**永遠 exit 0、永遠不擋**。會擋住工作的 hook 最後一定會被關掉。

> settings.json 在 session 啟動時載入，中途改不生效。

## 用法

```bash
dbp "一句話講清楚是什麼錯"        # 記一筆（唯一必填就是這句）
dbp "…" -w file.py:42 -t yaml,quoting -k machine
dbp fix <id> "後來怎麼解的"

dbp open                          # 未收尾清單（開場、收尾各跑一次）
dbp open "還沒驗證的事" -b "等服務重啟"
dbp done <id> "怎麼收的"

dbp risk <檔案>                   # 動手前：這個檔以前在哪摔過
dbp rules                         # 歸納：哪些類別重複出現
dbp sweep [目錄]                  # 清理：死引用 / 死 commit / 腐朽宣稱
dbp find <關鍵字> · dbp ls · dbp stats
```

### 完整迴路

```
錯誤 → 記錄 → 歸類 → 到閾值 → 變成機械檢查 → 該類永遠不再發生
```

**學習以「文件」收尾 = 沒落地。以「閘」收尾 = 落地了。**

`dbp rules` 跑出 `×2` 以上的類別，就不是零星 bug 了 —— 那是一個該從結構上關掉的類別。這時該做的是消滅整類，不是再修一個個案。

### 落地的操作定義

> **學到的東西必須在「動手的那一刻」出現，不是在「想起要查的那一刻」。**

那兩個時刻從不重合。實測：靠自律的記錄執行率只有 **25%**，而且全部發生在「停下來時」或「被罵時」。所以查詢也不能靠自律 —— 要交給 hook。

| | 落地了嗎 |
|---|---|
| 寫成文件 | ❌ 要人想起來讀 |
| 記進 log | ❌ 要人想起來查 |
| 手動 `dbp risk` | ❌ 同上 |
| **改檔當下自動跳出來** | ✅ 不需要想起來 |

### 三層測試的分工（一層抓不到另一層的東西）

| 層 | 問的問題 | 什麼情況叫失敗 |
|---|---|---|
| `tests/smoke.sh` | 裝完之後，這些功能還在嗎 | 已修好的東西又壞了（NEW_RED） |
| `redteam/` | 已知的那些洞今天還在嗎 | 狀態變了而沒人知道（DRIFT） |
| `cron/` | 錯誤史裡有沒有還沒被任何攻擊涵蓋的結構 | 排程安靜地什麼都沒做 |

第三層是**進料**，不是判決：它只產候選，不自動寫進 `redteam/attacks/`。
理由在 `cron/README.md` —— 2026-07-27 一天之內，一個有完整 repo 上下文的 agent
在專門偵測假綠的程式碼裡產了五個假綠。假紅在紅隊裡的傷害是複利的。

### 為什麼 `tests/smoke.sh` 不是全綠才算過

它現在是 **通過 6 · 已知紅 10 · exit 0**。

因為 `plan/001` 決定「先讓壞掉會叫，再去修壞掉」——
所以測試建立的那一刻，10 條已知洞**必須是紅的**。
每條斷言自帶 `EXPECT`：`KNOWN_FAIL` 紅了算通過，**綠了算 DRIFT**（洞被修掉卻沒人更新宣告）。

硬要 baseline 全綠只有兩條路，兩條都是這個 repo 自己禁的：
偷偷修掉（那 15 條靜默失效就失去護欄）、或偷偷跳過（抑制不掛牌）。

> **一支永遠全綠的 smoke test 是最貴的謊言。**

### `audit/` 與 `redteam/` 的分工

`audit/` 是**一次性快照**：那天、那台機器上，那些洞在。報告會腐朽。
`redteam/` 是**可重跑的攻擊**：`./redteam/run.sh` 隨時問「今天還在嗎」。

紅隊的語意是反的 —— **BREACH（攻擊成功／洞還在）才是符合預期**，
洞消失（SEALED）要停下來查是真修好還是攻擊瞎了，
而 **BROKEN（攻擊自己跑不起來）最嚴重**：那代表你什麼都不知道。
兩支 canary（`900`/`901`）專門監視 harness 自己會不會說謊。

**為什麼 snapshot 要機器產生**：手抄一份到 markdown 就是鐵律一禁的事。
但它的界線也要講清楚 —— 它證明「條目在 ledger 裡」，
**不證明「條目是真的」**。真假由 verification.md 的每一條指令負責。

## 設計約束（都是踩過才寫下來的）

- **永遠 exit 0。** 會中斷工作的記錄工具最後會被關掉。
- **沒事就完全安靜。** 每次都講話的東西會被當雜訊忽略。
- **假紅要當 P0 修。** 一個會誤報的閘會訓練人忽略所有閘，傷害大於價值。
  `sweep` 第一版誤報率 95%，是重大缺陷不是小問題。
- **抑制必須可見。** 每個豁免規則都是牆上的洞。洞可以有，但不能沒人知道它在。
  閘一旦擁有「什麼不算問題」的裁量權又沒人看著，它就從屠龍者變成龍。
- **規則必須能套在自己身上。** 豁免自己的規則系統就是惡龍。

## 真・複式簿記（迭代版）

三條鐵律合起來，本質是**複式簿記**。

> 2026-07-27 複驗前這裡寫「四條」，全文只定義三條 —— 自己的死引用，已修。

複式簿記（1494）解的問題與此完全相同：**如何在不信任記帳者的前提下，讓錯誤自己浮出來。**
方法不是找更誠實的會計，是同一筆事件記進兩本帳 —— **對不上就是有問題**。

但 AI 時代的版本有四點不同，缺一不可：

### 一 · 記的不是金額，是「宣稱 vs 證據」

記帳單位是一個陳述和它的支撐度。
對帳問的不是「數字對不對」，是**「這句話的確定性配不配得上它的證據」**。

### 二 · 至少一本帳不由被審者執筆

這是「真」字的來源。古典複式簿記兩筆都還是會計自己寫的。

| 帳本 | 誰寫的 | 獨立性 |
|---|---|---|
| `_edits` / `_runs` | harness | ⚠️ **半獨立（2026-07-27 降級）** |
| git history | git | ✅ 真獨立 |
| lint 輸出 / dbp 紀錄 | agent 自己的程式 | ⚠️ 半獨立 |
| **跨系統互驗**（如 A 系統驗 B 系統的成長與錯誤） | **另一個系統** | ✅ **最強** |

**對帳規則要優先建立在 agent 沒有筆的那幾本上。**

> **2026-07-27 降級記錄。** `_edits`/`_runs` 原本標「✅ 真獨立」，複驗證明是假的：
> 兩本帳都是 agent 家目錄下 644 的 JSONL，有 Bash 就有筆。實測三種攻擊全成功
> （偽造假 pytest 證據、`grep -v` 滅證、整本移走而 `dbp stats` 零抗議）。
>
> **但更精確的問題不是「不夠獨立」，是「兩本帳從未被拿來對過」** ——
> `unverified()` 是死碼、`main()` 零路由，沒有一行程式碼問過它們
> 「你們說的是同一件事嗎」。複式簿記能運作不是因為帳本難改，
> 是因為**改了對不上**。沒有對帳動作，帳本 B 的貢獻是 **0**，不是弱。
>
> 而 `hooks/dbp-risk-gate:41` 讓記帳發生在 `exists(DBP)` 檢查**之後** ——
> **帳本 B 依賴帳本 A 的工具存在，共同失效點，違反複式簿記唯一的成立條件。**
>
> `git history` 那一列的 ✅ 是真的，而且 **`_edits`/`_runs` 想做的事，
> `git log` + CI exit code 已經在做，且是真獨立的。**

### 三 · 迭代 —— 帳本種類會增生

古典簿記的科目表是固定的。這裡不是：

```
新的造假路徑出現 → 錯誤累積成類別 → 該類別長出新的帳本/檢查 → 對帳面積擴大
```

**因為造假路徑會演化，對帳規則就必須跟著演化。** 固定的科目表遲早被繞過。
這是「迭代版」的意思，也是它跟一次性稽核清單的根本差別。

### 四 · 審計者自己也在帳上

古典簿記不審計會計本身。這裡必須審 —— 否則屠龍者終將成為惡龍：

- 每個豁免/抑制規則都要**計數並印出來**（開洞可以，偷偷開不行）
- 法零指標：**豁免的成長速度 vs 真正修復的成長速度**。比值上升 = 在調鬆閘門而不是修對問題。

### 它防的不是舞弊，是漂移

古典簿記防的是**蓄意舞弊**。
這裡防的是**善意產生器的無意識漂移** —— 那才是 AI 真正的失效模式，而且更難察覺：
沒有壞人、沒有動機、每一步都合理，只是每一步都選了比較省事的那條。

**而它成立的關鍵性質：沒有任何一條法能藏住自己的漏網 —— 它的漏網會變成別本帳上的異常。**
