# coding 陰陽眼

**「coding 陰陽眼」= 三條鐵律合起來的總稱，不是單指第三條。**

| | | 擋什麼 |
|---|---|---|
| 一 | 事實只能推導，不能複製 | 當下說謊 |
| 二 | 0 信心路由 | 當下漏驗 |
| 三 | debug 百科（本 skill） | 未來重犯 |

名字是 Ryan 取的，2026-07-27 —— 那天一輪對話抓出 30 幾隻鬼，
其中三分之一是抓鬼的人自己當場生出來的。**看得見，才治得了。**

本 skill 負責第三條的執行面；一、二的實作在各專案的 lint / CI 裡。

## 這條鐵律要解什麼

鐵律一擋「抄來的假話」，鐵律二擋「只驗一次就當真」。**兩條都是單點防禦 ——
它們保證「這一次」被抓到，但同一種坑會在別的檔案、別的專案、別的 AI 身上重犯。**

沒有累積，每次都是第一次。

## 鐵律三

> **任何錯誤只要被抓到一次 —— AI 抓、人抓、機器抓都算 —— 就立刻標記收錄。**
> **標記成本必須低到不會有人偷懶跳過。**

低成本是設計核心，不是方便性考量：**只要標記有一點麻煩，忙的時候就會被跳過，
而忙的時候正是最會出錯的時候。**

## 怎麼記（一行，別想太多）

```bash
dbp "一句話講清楚是什麼錯"
```

最低標準只有一個：**未來的 AI 讀得懂、定位得到、不會誤會。** 達到就夠了，
不要為了寫得完整而拖延 —— 記了不完美 >>> 完美但沒記。

有餘力再加：

```bash
dbp "yaml 純量裡出現 at: 被當成 mapping key" -w topology.yaml:48 -t yaml,quoting
dbp "~ 在雙引號裡不展開，4 個真實路徑被誤報" -w verify.sh -k human -t shell
```

| 旗標 | 用途 |
|---|---|
| `-w` | 位置：`檔案:行號` / 指令 / URL / repo |
| `-k` | 誰抓到：`ai`（預設）· `human` · `machine`（測試/CI/lint） |
| `-t` | 標籤，逗號分隔。之後聚合用 |
| `-e` | 證據：錯誤訊息關鍵一行、可重現的指令 |

後來解掉了就補上，**不改舊行**（append-only）：

```bash
dbp fix <id> "改用 os.path.expanduser，不經 shell 引號"
```

## 什麼時候記（不要等人叫你）

**一律記：**
- 測試紅、CI 失敗、lint 報違規、指令非零退出
- 你發現自己前面的判斷/修改是錯的
- Ryan 指出錯誤（`-k human`）
- 文件宣稱與實際不符
- 環境陷阱（版本、路徑、引號、權限、快取）
- 舊修復失效或回歸

**不用記：**
- 打錯字當場改掉、沒有下一個人會踩到的
- 純粹是使用者改主意（那不是錯誤）

拿不定就記。**假陽性的成本是一行 JSON；漏記的成本是下次有人再踩一遍。**

## 第二種收錄對象：未收尾的事（與 bug **同級**）

**這不是 bug 的附屬品，是並列的另一類。** 兩者同級，理由是它更陰險：

| | 會不會叫 | 會不會痛 | 結果 |
|---|---|---|---|
| bug | 會（紅字 / exit code） | 會 | 被處理 |
| **未收尾** | **不會** | **不會** | **不被處理 → 長大** |

**不會叫、不會痛的東西不會被處理；不被處理就會長大 —— 這就是亞健康的因子。**
bug 是急症，未收尾是慢性病。慢性病不會讓你今天倒下，它讓你某天突然倒下。

錯誤有人抓、有紅字、有 exit code；
「還沒做完的下一步」只活在對話裡，視窗一關就沒了，然後變成幾個月後的大患。

2026-07-27 實例：一輪對話結尾列了 5 條「做了但驗不了 / 還沒做 / 等人點頭」，
全部只存在於一則聊天訊息。沒有任何機制會再提起它們。

```bash
dbp open                             # ← session 開場先跑這個
dbp open "做了但還沒驗證的事"
dbp open "等重啟才生效" -b "等 Ryan 決定誰重啟"
dbp done <id> "後來怎麼收的"
```

`-b` 是被誰擋住。它會把清單分組，讓「我還沒做」和「在等人」分開 ——
兩者的處置完全不同，混在一起就會互相掩護。

**什麼時候要 `dbp open`（一律記，別判斷）：**
- 你說了「之後再…」「下一步…」「還沒…」「等 X 就…」
- 你改了東西但沒驗證，或驗不了（服務沒重啟、要等下個 session、缺權限）
- 你問了使用者一個問題但還沒得到答案
- 你發現一件該做的事但不在當前任務範圍內

**開場與收尾都要跑 `dbp open`。** 開場是為了接上，收尾是為了不掉。

## 動手前先查（這才是收錄的目的）

要修 bug、要碰陌生模組、要重跑一個以前失敗過的流程 —— **先查有沒有人踩過**：

```bash
dbp find yaml          # 關鍵字
dbp ls 30              # 最近 30 筆
dbp stats              # 誰最常抓到、哪個 repo 最常出事、什麼標籤最多
```

`dbp stats` 是大數據整理的入口。當某個標籤累積到一定量，那就不是零星 bug，
**是一個該從結構上解決的類別** —— 那時該做的是消滅那個類別，不是再修一個個案。

## 存在哪

`~/.debugpedia/YYYY-Www.jsonl`（ISO 週輪替，append-only）。
可用 `DEBUGPEDIA_DIR` 覆蓋。工具本體：`~/.local/bin/dbp`。

寫入失敗**不會擋住你**（印 stderr、exit 0）—— 一個會中斷工作的記錄工具，
最後一定會被關掉。

## 與另外兩條鐵律的關係

| | 擋什麼 | 落在哪 |
|---|---|---|
| 一 · 事實只能推導不能複製 | 抄來的假話 | 有 `brain/lint.py` 的專案由它擋 |
| 二 · 0 信心路由 | 只用同一條路驗就當真 | 同上 · 加反向測試 |
| **三 · debug 百科** | **同一種坑重複踩** | **`dbp`（本 skill，全域）** |

前兩條的**正文與實作細節去該專案的 `brain/lint.py` 檔頭讀**，這裡不複述、
也不寫檢查代號 —— 代號會漂（今天就從五道變七道），寫死就是抄本。
沒有 `lint.py` 的專案，前兩條靠人守；第三條到哪都能用。

三條一起看：**一防當下說謊，二防當下漏驗，三防未來重犯。**
