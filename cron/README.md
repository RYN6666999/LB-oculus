# cron/ — 讓錯誤史自己餵養紅隊

> **鐵律三的下一段。**
> 「任何錯誤只要被抓到一次就立刻收錄」解決了記錄，沒解決**利用**。
> 累積起來的知識躺在 ledger 裡不會自己變成防線。
> 這一層負責把「累積」翻譯成「紅隊打得動的假說」。

規劃與取捨見 [`plan/002`](../plan/002-llm-generalizer-cron.md)。

## 為什麼需要 LLM（`dbp rules` 不夠）

| | 產出 | 餵得動紅隊嗎 |
|---|---|---|
| `dbp rules`（統計） | 「shell 標籤出現 7 次」 | ✗ 打不到任何具體的行 |
| 這一層（推理） | 「這 7 次的共同結構是『退出碼被複合指令吃掉』，所以任何 `if cmd; then` 之後取 `$?` 的地方都該有一支攻擊」 | ✓ 可以直接寫成 attack |

差別不是「更聰明」，是**跨檔的同型結構統計看不見** ——
那 7 筆分別掛在 install / redteam / smoke / cron 四個標籤下，
在任何統計裡都不會聚成一堆。

## 為什麼**不**自動生成 attack 檔

這是整個設計最重要的一條約束，理由是實證的，就發生在 2026-07-27：

> 同一天，一個有完整 repo 上下文的 agent，
> **在專門偵測假綠的程式碼裡，產了五個假綠。**
>
> 1. `redteam/attacks/001` 的假 SEALED —— `grep 'exit 127'` 掃到的是一句無條件印出的說明文字
> 2. `tests/smoke.sh` 的 A06 —— 照抄 plan/001 的斷言，而那條斷言驗不到它宣稱要驗的洞
> 3. plan/002 的 payload 驗收設計 —— 「空檔案」和「乾淨的檔案」在 `grep -c` 眼裡一樣
> 4. `generalize.py` 排除 `evidence` 欄位 —— 遮罩「有效」是因為東西根本沒送，那條正則從沒被執行過
> 5. 心跳把 stdout 的進度訊息當成死因記下來

一個只讀得到 ledger 摘要、沒有 repo 上下文的 LLM，只會更糟。

而假紅在紅隊裡的傷害是**複利**的 —— `redteam/README.md` 自己寫了
「假紅會訓練人忽略全部的紅」。一支自動長出 30 支垃圾攻擊的 cron，
會讓整層測試在兩週內變成沒人看的雜訊。**那比沒有這一層更糟。**

所以邊界劃在這裡：

| cron 做 | cron 不做 |
|---|---|
| 讀 ledger → 去識別化 → 送 LLM → 存候選 | 寫進 `redteam/attacks/` |
| 產出「假說 + 建議 EXPECT + 該打哪個檔」 | 產出可執行的 `.sh` 讓 `run.sh` 撿去跑 |
| 記一筆 `dbp open`（會過期、會叫） | 自動 commit / push |
| LLM 掛掉時**大聲失敗** | 安靜 exit 0 |

**人（或有 repo 上下文的 agent）必須在中間。**

## 這一層學到的規則（比程式碼值錢）

### 1 · 拿「某字串不存在」當證據前，必須先證明檢查真的執行到了

一天之內犯五次的那個病。它的通用形狀是：

```
斷言「輸出裡沒有 X」→ 通過 → 判定安全
                       ↑
              但輸出根本是空的
```

`grep -c` 分不出「乾淨」和「什麼都沒收到」。`test -e` 分不出
「能執行」和「symlink 存在但解譯器不見了」。**同一個病。**

正確順序永遠是兩段：

```sh
[ -s "$PAYLOAD" ] || return 2              # 先證明攔到了東西
grep -q "$KNOWN_MARKER" "$PAYLOAD" || return 2   # 且是這次的東西
grep -q 'sk-' "$PAYLOAD" && return 1       # 才有資格說它乾淨
```

護欄在 `tests/smoke.sh` 的 A15。反向驗證做過：把 payload 改走 argv，
A15 報 **BROKEN**（不是 PASS）—— 舊設計在這裡會綠著放行機密。

### 2 · 進度訊息和死因必須走不同的流

心跳第一版用 `2>&1` 合併後「取最後一行當失敗原因」，
結果心跳誠實地記下了 `去識別化命中 2 處` —— 一句進度報告。

**一個把進度當死因記下來的心跳，比沒有心跳更糟：它會誤導追查方向。**
所以 `generalize.py` 的所有 `fail()` 只寫 stderr，那是它對外殼的契約。

### 3 · 排除一個欄位不是「保護」，是把防線關掉

第一版把 `evidence` 從送出欄位裡排除，理由是「它最可能含機密」。
結果遮罩那條正則**從來沒有被執行過**，而驗收看起來是綠的。

真正的防線是「送出前遮罩」，而遮罩只有在**真的有東西經過它**時才會被驗證。
所以現在 `evidence` 一定送、一定過 `scrub()` ——
讓那條防線每天被實際使用一次，它才有可能在失效那天被發現。

### 4 · 遮罩策略必須是黑名單兜底，不是白名單列舉

「列出所有密鑰格式」是註定失敗的白名單思維 —— 世界上的 key 格式
比任何人想得到的多。所以 `scrub()` 是兩層：

1. 已知格式精準遮罩（`sk-` / `ghp_` / `AKIA` / JWT / Bearer / URL 內帳密）
2. **任何長度 ≥20 的混合大小寫數字連續字串一律遮掉**

誤遮的代價是 LLM 少看到一點細節；漏送的代價是使用者的 key 進了別人的日誌。
**不對稱，所以寧可誤遮。**

### 5 · 遮了幾處必須印出來

`0 處命中` 有兩種可能：真的沒機密，或**正則全部失效**。
兩者長得一樣，所以要印出來並明講第二種可能。抑制必須可見。

## 用法

### 設定 LLM（刻意不預設任何供應商）

指令從 **stdin** 收 prompt，把回應印到 **stdout**。就這個契約，其餘自由。

```sh
export DBP_LLM_CMD='llm -m gpt-4o'          # simonw/llm
export DBP_LLM_CMD='claude -p'              # Claude Code
export DBP_LLM_CMD='ollama run qwen2.5'     # 本機模型（機密完全不出門）
```

硬綁一家等於幫你決定你的帳單。**本機模型是最安全的選擇** ——
但去識別化仍然照做，因為「我以為它沒出門」跟「它沒出門」是兩件事。

### 手動跑一次（**排程前必做**）

```sh
sh cron/generalize.sh
```

一個沒有手動成功過的排程不該被排進 crontab —— 那只是把失敗藏到看不見的地方。

### 排進 crontab（本層刻意不代你做）

```cron
# 每週一 09:00。絕對路徑是必要的：cron 的 PATH 通常只有 /usr/bin:/bin
0 9 * * 1 cd $HOME/Developer/LB-oculus && DBP_LLM_CMD='llm -m gpt-4o' /bin/sh cron/generalize.sh >> /tmp/dbp-cron.log 2>&1
```

改你的 crontab 是有副作用的全域操作，跟 `settings.json` 同一條理由：
**印指令給你看，不代替你做。**

### 確認它真的在跑（換一條路，別讀 log）

```sh
bash tests/smoke.sh        # A14 會去讀心跳並驗證它誠實
cat cron/_heartbeat.json
```

心跳**不由 cron 自己檢查** —— 那是共同失效點，
`plan/001` 已經推翻過一次這個錯（「heartbeat 也走同一個 shebang」）。

## 候選怎麼變成攻擊

`cron/candidates/YYYY-MM-DD.md` 裡每條都附了三步，缺一不可：

1. **讀被指的那個檔** —— 確認假說針對真實程式碼，不是想像的程式碼
2. **故意把洞補起來，確認攻擊會翻態** —— 不會紅的測試不是測試
3. **確認不是既有攻擊的重複** —— 重複的紅跟假紅一樣會訓練人忽略

第 2 步是門檻。`redteam/README.md` 的規矩對機器產的候選一樣適用，
**沒有豁免**。
